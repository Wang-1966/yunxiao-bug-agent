# Agent 执行器修复与整体方案

日期：2026-10-10。本文依据当时源码和失败任务日志。

后续进展：P0 交付闭环见 [修复交付闭环](AGENT_DELIVERY.md)。编码执行已改为 Pi，不再使用文中的 JSON 动作协议与 `repair_executor` 通用编辑循环。当前调用链以 [README](../README.md) 和 [Pi 执行内核](../backend/docs/pi-conversation.md) 为准。

## 结论

建议保留当前受限源码工具、隔离工作树和两次人工确认流程，完善已有单 Agent 工作流。当前瓶颈来自协议、上下文交接和任务生命周期，不需要增加 Agent 数量、引入新框架或将模型放开为任意 Shell 执行器。

本次修复解决“有效操作与错误共用 30 轮额度、分析与修复收敛目标混用、修复阶段重复寻找源码、最后一轮无法结束确认”的问题。后续优先补齐验收提交与合并闭环，再统一首次执行和恢复执行的调度与状态管理。

## 已核对的调用链

1. `api/agents.py` 接收任务，`core/orchestrator.py` 更新 SQLite、提交优先队列并控制首次任务并发。
2. `agent/graph.py` 执行获取详情、工作树准备、源码分析和方案生成；调度器启用方案确认后暂停图。
3. `agent/nodes.py` 通过阶段模型配置调用 `llm/factory.py`、`llm/unified_client.py`；图片经 `bug_media.py` 加载并由 `bug_visual.py` 转为持久文字观察。
4. `repair_executor.py` 提供路径受限的浏览、读取、搜索和精确替换工具；模型返回 JSON 动作，真实 Git 和命令结果用于判定修改与验证。
5. 用户确认方案后，调度器从 `task_history.result` 恢复数据；补充反馈触发重新分析，无反馈进入修复。
6. `verify_worktree` 执行项目保存的命令；通过后进入验收。`repair_review.py` 处理确认，`repair_merge.py` 合并并清理工作树。
7. 前端 `AgentList.tsx` 与 `RepairReview.tsx` 轮询状态和审查差异；WebSocket 广播工具存在，但未接入上述执行链。

另核对了 `tools/code_analyzer`、`tools/git_operator` 和 `tools/test_runner`：这些旧工具没有接入当前生产工作流，不能将它们的能力视为当前 Agent 已实现的功能。

## 本次失败的证据

任务 `agent-task-ad0f76d4` 的修复阶段在北京时间 18:21–18:23 运行，模型为 `grok-4.7`。30 个请求包含 1 次目录浏览、9 次搜索、12 次读取和 8 次 `Extra data` JSON 解析失败；没有 `edit`。失败工作树的 `git status --short` 为空。

分析阶段已形成高置信度根因，但修复阶段重新开始独立源码会话，仅继承文字根因与方案。每个请求都占用同一额度，包括协议错误；临近上限又提示使用分析阶段的 `confidence=low` 与 `finish`，未保证实际写入。第 30 次请求后无额外结束机会。

日志未保存原始无效响应，不能确认其额外内容究竟是第二个 JSON 对象、注释还是其他文字。因此本次保持严格单对象解析，不猜测、不截取第一段后执行。

## 本次已实施

| 改动 | 正确性和兼容性保障 |
| --- | --- |
| 保持单 JSON 对象协议，解析错误明确指出拼接问题 | 不吞掉尾部数据，不擅自执行部分动作；原单动作仍兼容 |
| 新增最多 5 个只读动作的 `batch` | 仅支持 list/read/search；禁止嵌套、修改、看图和结束；每项沿用路径校验与去重 |
| 将 30 轮有效源码操作与错误重试分开 | 连续 3 次或累计 10 次失败停止；不因错误减少有效操作，但也不无界重试 |
| 为有效操作耗尽后的 finish 单独预留请求 | 禁止继续读写；无法完成返回 blocked_reason 并保存已有修改 |
| 分析、修复使用不同收敛目标，每次请求显示剩余预算 | 修复先核对已确认方向，再真实 edit；不足时明确失败，不能伪报完成 |
| 提前 finish 且无 Git 差异时返回纠正反馈 | 模型可以继续修改；反复伪报完成会停止；节点仍独立检查真实差异 |
| 保存最多 12 个源码阅读位置至任务状态 | 不存整段源码；修复开始重新读取最新文件，总输入上限 48,000 字符；旧任务无此字段仍可运行 |
| 无效 read 不授予修改权限 | 必须成功读取后才能替换已有文件 |
| 应用 agent_timeout 为每个源码阶段的总时限 | 每次模型请求仍最多 120 秒，总阶段也有截止时间；超时取消调用，保留工作树 |
| 方案生成错误时图立即结束 | 保留历史直接调用模式，防止失败后继续进入修复节点 |

批量中单项失败会逐项返回反馈；至少一项成功时算一轮有效操作，全失败计入错误。批量不扩大写入能力。截图按需重读仍需提供文字观察，原图在消费一次后卸载。

## 后续最优改造顺序

### P0：补齐验收、提交与合并闭环

目前执行器明确禁止模型提交，验证节点也未创建提交，`repair_merge.py` 却直接合并 Agent 分支。这意味着单靠当前流程，工作树中的未提交修改不会随分支合并。

建议验收绑定已审查差异指纹、基础提交和目标分支；验证通过后由系统创建隔离分支上的本地提交，记录提交 SHA，用户确认后合并该 SHA。验收前确认工作树内容与验证对象一致；目标仓库不干净继续拒绝，绝不覆盖用户修改。Git 提交/合并应在 SQLite 长事务外执行，使用任务状态预占和条件更新完成交付，避免 Git 与数据库状态相互锁死。合并成功与清理失败分别记录，让清理可重试。

验收：干净目标仓库最终获得真实修复；拒绝、冲突、目标脏工作树、进程中断和清理失败均保留可恢复证据，不误标成功。

### P1：统一任务执行和恢复调度

首次任务通过优先队列受 `max_concurrent_agents` 限制，`confirm_proposal` 直接 `create_task` 恢复执行，能够绕过并发上限。首次与恢复还分别维护图消费、进度、错误处理逻辑，存在漂移风险。

建议用同一队列承载首次、重分析和修复恢复任务，同一执行函数消费图并更新状态。确认操作只完成原子状态转移并入队。完成回调应校验当前 handle 身份，避免旧回调清除新的运行记录。

验收：任意混合首次/恢复任务均不突破并发限制；停止排队和运行任务一致；重复确认不产生重复执行。

### P1：真实暂停和可恢复状态

`pause` / `resume` API 当前只返回成功文案，没有改变执行。`add_logging_node` 也只是占位，不会实际添加验证日志；低置信度等待函数未接入图。

建议暂停发生在工具操作边界，不打断写入批次；暂停、恢复、取消分别有真实状态与行为。持久化执行检查点应包含阶段、源码位置、成功操作记录与已修改文件，仍从工作树读取当前内容。先实现边界暂停和阶段恢复，再按实际需求增加操作级恢复；不保存带图片和签名 URL 的原始对话。需要日志确认的任务明确进入人工补证或生成可确认的诊断方案，不伪装已添加日志。

验收：暂停后不再执行新操作；服务重启可确认恢复条件；重复恢复不会创建并行任务；工作树内容不会被重置。

### P2：验证反馈与可观测性

目前命令验证失败直接结束，不会在授权修复范围内将错误反馈给模型。建议将退出码、有限输出和当前差异交给一次受限修正循环，复用预算与超时；仍只运行项目配置命令，不允许模型自行安装依赖或修改验证标准。

日志应保存阶段、请求序号、动作、有效额度、协议/工具错误类别、耗时、修改数和终止原因。现有批量日志记录每项只读请求及成功数；后续将页面日志与完整诊断日志分层，避免原始响应泄露正文或敏感源码。前端显示实际阶段进度，不将等待确认视为完成。

验收：同一失败能区分协议、源码工具、模型超时和验证错误；验证修正次数有界；无真实差异或未通过命令不进入验收。

### P2：移除失效和重复实现

当前生产路径使用 `repair_executor`；旧 GitOperator 会强制删除同名工作树，旧 TestRunner 在 async 函数中同步运行命令。建议确认无外部调用后删除旧工具、未接入的等待分支和空实现，保留一个真实执行入口。此项与本次轮次故障无直接关系，未擅自删除。

## 验证与限制

最终执行：`cd backend && python3 -m pytest tests/test_repair_executor.py tests/test_agent_tasks.py tests/test_unified_client.py -q --asyncio-mode=auto`。结果：42 项通过，1 项既有验收合并场景失败，原因是目标仓库存在未提交修改而被安全检查拒绝。执行器新增场景全部通过；本次修改的 5 个 Python 模块通过 AST 语法解析。

新增回归使用临时 Git 仓库和模拟模型响应，覆盖拼接 JSON 拒绝、独立错误预算、连续/累计失败限制、只读批量边界、源码恢复读取最新内容、提前 finish 后继续修改、有效额度耗尽后结束、无效 read 权限、阶段超时取消，以及方案失败不进入修复。现有完整流程测试覆盖隔离、真实差异、命令验证和人工确认。

执行测试需添加 `--asyncio-mode=auto`，否则现有异步数据库 fixture 不会执行；这会产生误导失败甚至创建名称为 coroutine 字符串的数据库文件。建议后续集中配置测试模式。

未调用付费模型或自动重新执行用户的失败任务，因此本次不能承诺 Grok 实际修复一定成功；它仍可能在协议持续无效、证据不足、操作额度或时限耗尽时明确失败。全工作流中目标仓库带未提交修改却期望合并成功的既有测试与当前安全约束冲突，须在 P0 合并闭环改造时拆分为“脏仓库拒绝”和“干净仓库合并”两类场景。
